## 1. Spike A — 네이티브 빌드가 되는가

### 왜 이걸 먼저 했나

헌장 §11이 **"기능을 다 만든 뒤에 네이티브 빌드를 시도하지 말 것"**이라고 못 박았다.
GraalVM native-image는 리플렉션을 쓰는 라이브러리에서 자주 깨지는데, 그 사실을
Day 18에 알게 되면 3주 일정이 통째로 무너진다.

그래서 **판정 로직을 한 줄도 쓰기 전에** 빌드 파이프라인부터 세웠다.

### 환경에서 발견한 것

| 항목 | 상태 |
|---|---|
| Java Temurin 21.0.10 | 있음 |
| Gradle | **없음** |
| GraalVM `native-image` | **없음** ← 최대 리스크 |
| gcc 11.4 / zlib / 메모리 30G | 있음 (native-image 전제조건 충족) |
| `sudo` | **비밀번호 요구** |

sudo를 쓸 수 없어서 툴체인을 **홈 디렉토리 설치(SDKMAN)로 제한**했다.
그 결과 예상 밖의 문제가 하나 나왔다 — 시스템에 `zip`이 없어서 SDKMAN 설치 스크립트가
실패했고, Codex가 Info-ZIP을 `~/.local/bin`에 직접 빌드해서 우회했다.

### 결과

| 항목 | 실측값 |
|---|---|
| native 빌드 | **17초** (clean 기준) |
| 바이너리 | 17MB, **단일 파일** |
| 시작 시간 | **0.004s** |
| core 테스트 | 2개 통과 |

- GraalVM CE **21.0.2** — SDKMAN이 제공하는 21 LTS 라인의 유일한 버전
  (상위는 25.2.4이고 JDK 25 기반이라 헌장 §3의 Java 21 고정과 충돌한다. 올리지 않았다)
- picocli-codegen이 `reflect-config` / `proxy-config` / `resource-config`를 자동 생성 →
  **리플렉션 문제가 애초에 없었다**

### Codex 보고를 그대로 승인하지 않은 지점

Codex의 `./gradlew build` 출력이 **전부 `UP-TO-DATE`**였다. 테스트가 실제로 실행됐다는
증거가 없다. `clean build`로 재실행해서 `tests="2" failures="0"`을 직접 확인했다.
네이티브 빌드도 clean 상태에서 다시 돌려 17초를 확인했다.

`core`에 네트워크·파일 I/O·`System.out`이 없는지도 grep으로 검증했다 (없음).

### CI에 반영해야 할 제약 (실측)

1. **`configuration-cache`를 켜지 말 것** — NBT 0.10.4의 `generateResourcesConfigFile`이 실패한다
2. **Gradle 8.x 고정** — `cli`에서 Gradle 9.0 deprecation 경고 발생
3. **`JAVA_HOME` 명시** — GraalVM toolchain 자동 감지가 꺼져 있다

커밋: `2e78961`

## 2. Spike B — PDFBox를 넣을 수 있는가 → **아니오**

### 왜 별도 스파이크로 쪼갰나

Spike A에 PDFBox를 같이 넣었으면 실패했을 때 **원인이 골격 때문인지 PDFBox 때문인지
분리할 수 없다.** 그래서 골격이 먼저 서는 것을 확인한 뒤, PDFBox만 따로 붙였다.

`spike/pdfbox` 브랜치에서 격리 실행하고, **90분 타임박스**와
"오류 클래스 10개 초과 시 즉시 FAIL 판정"을 지시서에 걸었다.
억지로 성공시키는 게 목적이 아니라 **v0.1에 PDF를 넣을지 결정**하는 게 목적이었기 때문이다.

### 결과

| 경로 | 결과 |
|---|---|
| JVM | ✅ 텍스트 추출 성공 |
| `nativeCompile` 빌드 | ✅ 성공 (25.2s) |
| **네이티브 실행** | ❌ `Fatal error reported via JNI: Could not allocate library name` |

### Codex가 놓친, 더 결정적인 근거

Codex는 런타임 JNI 오류를 실패 근거로 들었다. 그런데 산출물 목록을 보니
실행 파일 옆에 **AWT 사이드카 `.so` 8개**가 생성돼 있었다.
직접 격리 테스트를 해봤다:

```
$ cp ats-check /tmp/ && /tmp/ats-check --resume resume.pdf
UnsatisfiedLinkError: No awt in java.library.path
```

**JNI 오류를 고쳐도 소용없다.** 배포 산출물이 `17MB 파일 1개` → `43MB 파일 9개`가 되고,
"바이너리 하나 받아서 실행"이라는 제품 전제 자체가 무너진다.
이건 튜닝으로 풀 문제가 아니라 스코프 결정이 필요한 문제다.

### 기각한 우회책

1. PDFBox JAR의 GraalVM 메타데이터 → **없음**
2. Reachability Metadata Repository 활성화 → 빌드 통과, **런타임 실패 동일**
3. 수동 `reflect-config` → **불가.** `MissingReflectionRegistrationError`가 안 떠서
   등록할 클래스를 특정할 수 없었다
4. `-H:+AddAllCharsets` → charset 경고만 해소
5. `--initialize-at-build-time` → **빌드 실패.** 22개 이상 연쇄 초기화
   (`java.awt.Toolkit`, `BufferedImage`, `ICC_Profile` …)

### 결정

**이력서 파싱(PDF/DOCX)을 v0.2로 연기.** 헌장 §11이 미리 정해둔 분기를 그대로 실행했다.

제품은 성립한다 — §7이 `profile.yml`만으로 전 단계가 동작하도록 설계해뒀기 때문이다.
이력서 파싱은 편의 기능이지 전제가 아니다.

DOCX(POI)는 실측하지 않았다. AWT 결합이 더 심해 같은 실패가 예상되므로,
두 번째 스파이크에 시간 쓰는 대신 이력서 경로 전체를 일관되게 미뤘다.
**추정이라는 점을 ADR-005에 명시했다.**

실험 코드는 `spike/pdfbox` 브랜치에 보존하고 병합하지 않았다.

커밋: `98fdfa6` / 문서: `docs/adr/ADR-005-no-pdf-parsing-in-v0.1.md`

## 3. 헌장 개정 반영

사용자가 `save`/`open`/프론트매터/상태추적을 추가했다. 반영하면서
**네이티브 빌드를 깨뜨릴 수 있는 신규 리스크 2건과 규격 충돌 1건**을 함께 확정했다.

| # | 문제 | 조치 |
|---|---|---|
| 1 | `save`가 클립보드를 AWT로 읽으면 **PDFBox와 똑같이** `java.desktop`을 끌어온다 | 외부 명령 위임 (`wl-paste`/`pbpaste`/`Get-Clipboard`), `open`도 `xdg-open`/`open`/`start` |
| 2 | `save` 성공(exit 0)이 **"APPLY"와 구분되지 않는다** | `check`만 판정 코드(0/1/2), 나머지 서브커맨드는 `0=성공` |
| 3 | 저장된 공고 원문이 **공개 레포에 커밋될 수 있다** | `jobs/`를 `.gitignore`에 (§9 익명화 정책과 충돌) |
| 4 | SnakeYAML 클래스 바인딩은 리플렉션 메타데이터를 요구 | `Map` 파싱 후 수동 매핑 |
| 5 | OSC 8 하이퍼링크가 파이프에 섞이면 스크립트 연동이 깨진다 | 비-TTY에서 자동 비활성화 |

DoD에 **"각 바이너리가 단일 파일이다"**를 추가하고, CI 스모크 테스트는
바이너리를 다른 디렉토리로 복사해서 실행하도록 명시했다. 같은 함정을 CI가 잡는다.

§2 판단 기준에도 4번을 추가했다: **"단일 바이너리 배포를 깨뜨리는가"**

## 5. Task 1 — 섹션 분류기

### 설계에서 보완한 것

헌장 §6은 2층 신호(섹션 헤더 + 문장 어조)를 제시한다. 그런데 **그것만으로는
§6 자신의 예시를 처리할 수 없다:**

```
"Working knowledge of Finnish"   → §6은 REVIEW를 원한다
```

이 문장이 `Requirements:` 섹션 안에 있으면 2층 신호로는 REQUIRED가 되어버린다.
그래서 **완화 표현(hedge)을 3층 신호로 추가**했다 —
`working knowledge`, `basic`, `conversational` 등이 확신을 깎는다.

결합 규칙을 10행 표로 확정하고 전부 테스트로 덮게 지시했다.

### Codex 산출물

- 모델 4개(`RequirementLevel`, `SectionKind`, `Signal`, `Clause`) + 분류기 4개
- 테스트 18개 통과, `core` 런타임 의존성 여전히 0개
- §6의 세 예시 정확히 동작 ✅

보고서 §6("스스로 결정한 것")을 성실히 채웠고, §8에서 **자기 산출물의 리스크를
정확히 지적**했다. 그 지적이 맞는지 직접 확인했다.

### 2차 검증에서 잡은 결함 3건

컴파일된 클래스를 직접 호출해 실제 공고 패턴을 넣어봤다:

| 입력 | 결과 | 문제 |
|---|---|---|
| `Finnish is not required.` | **REQUIRED** ❌ | **치명적.** 핀란드어가 *불필요*한 좋은 공고를 SKIP시킨다. 도구 목적과 정반대 |
| `Benefits:` → `Free Finnish lessons.` | **REQUIRED** ❌ | 복지를 필수 요건으로 오독. 핀란드 회사가 "Finnish lessons provided"를 복지로 적는 건 흔하다 |
| `Requirements include Java and Kotlin.` | **절이 0개** ❌ | 헤더로 오탐되어 요건이 통째로 소실 |

**왜 이게 지금 중요한가:** 판정 규칙(Task 2)이 이 분류기 위에 얹힌다.
분류가 틀리면 언어·연차·학위·스킬 규칙이 전부 틀린다. 다음 단계로 넘어가기 전에 고쳐야 한다.

### Task 1.5 — 수정 지시 (진행 중)

1. **부정 신호를 4번째 축으로 추가** — `RequirementLevel.NEGATED` 신설.
   `NICE`로 뭉뚱그리지 않는다. "있으면 좋다"와 "필요 없다"는 의미도 출력 문구도 다르다.
   대조 접속사(`but`, `however`)가 있으면 부정 범위가 불확실하므로 `AMBIGUOUS`
2. **헤더 판정을 형태 기반으로** — 문장 종결 부호로 끝나는 줄은 헤더가 아니다
3. **미지 헤더에서 섹션 상태 리셋** — 모르면 중립으로 두는 것이 §6의 "단정하지 않는다" 원칙에 맞다.
   중립 헤더 사전(`benefits`, `perks`, `about us`, `tech stack` …)도 명시

재현 케이스 3건을 그대로 테스트로 넣게 했고, **기존 18개 테스트 회귀 금지**를 조건에 걸었다.
