## 1. Spike A — 네이티브 빌드가 되는가

### 왜 이걸 먼저 했나

헌장 §11이 **"기능을 다 만든 뒤에 네이티브 빌드를 시도하지 말 것"**이라고 못 박았다.
GraalVM native-image는 리플렉션을 쓰는 라이브러리에서 자주 깨지는데, 그 사실을
Day 18에 알게 되면 3주 일정이 통째로 무너진다.

그래서 **판정 로직을 한 줄도 쓰기 전에** 빌드 파이프라인부터 세웠다.

### 환경에서 발견한 것

| 항목 | 상태 |
|---|---|
| Java Temurin 21.0.10 | 있음 |
| Gradle | **없음** |
| GraalVM `native-image` | **없음** ← 최대 리스크 |
| gcc 11.4 / zlib / 메모리 30G | 있음 (native-image 전제조건 충족) |
| `sudo` | **비밀번호 요구** |

sudo를 쓸 수 없어서 툴체인을 **홈 디렉토리 설치(SDKMAN)로 제한**했다.
그 결과 예상 밖의 문제가 하나 나왔다 — 시스템에 `zip`이 없어서 SDKMAN 설치 스크립트가
실패했고, Codex가 Info-ZIP을 `~/.local/bin`에 직접 빌드해서 우회했다.

### 결과

| 항목 | 실측값 |
|---|---|
| native 빌드 | **17초** (clean 기준) |
| 바이너리 | 17MB, **단일 파일** |
| 시작 시간 | **0.004s** |
| core 테스트 | 2개 통과 |

- GraalVM CE **21.0.2** — SDKMAN이 제공하는 21 LTS 라인의 유일한 버전
  (상위는 25.2.4이고 JDK 25 기반이라 헌장 §3의 Java 21 고정과 충돌한다. 올리지 않았다)
- picocli-codegen이 `reflect-config` / `proxy-config` / `resource-config`를 자동 생성 →
  **리플렉션 문제가 애초에 없었다**

### Codex 보고를 그대로 승인하지 않은 지점

Codex의 `./gradlew build` 출력이 **전부 `UP-TO-DATE`**였다. 테스트가 실제로 실행됐다는
증거가 없다. `clean build`로 재실행해서 `tests="2" failures="0"`을 직접 확인했다.
네이티브 빌드도 clean 상태에서 다시 돌려 17초를 확인했다.

`core`에 네트워크·파일 I/O·`System.out`이 없는지도 grep으로 검증했다 (없음).

### CI에 반영해야 할 제약 (실측)

1. **`configuration-cache`를 켜지 말 것** — NBT 0.10.4의 `generateResourcesConfigFile`이 실패한다
2. **Gradle 8.x 고정** — `cli`에서 Gradle 9.0 deprecation 경고 발생
3. **`JAVA_HOME` 명시** — GraalVM toolchain 자동 감지가 꺼져 있다

커밋: `2e78961`

## 2. Spike B — PDFBox를 넣을 수 있는가 → **아니오**

### 왜 별도 스파이크로 쪼갰나

Spike A에 PDFBox를 같이 넣었으면 실패했을 때 **원인이 골격 때문인지 PDFBox 때문인지
분리할 수 없다.** 그래서 골격이 먼저 서는 것을 확인한 뒤, PDFBox만 따로 붙였다.

`spike/pdfbox` 브랜치에서 격리 실행하고, **90분 타임박스**와
"오류 클래스 10개 초과 시 즉시 FAIL 판정"을 지시서에 걸었다.
억지로 성공시키는 게 목적이 아니라 **v0.1에 PDF를 넣을지 결정**하는 게 목적이었기 때문이다.

### 결과

| 경로 | 결과 |
|---|---|
| JVM | ✅ 텍스트 추출 성공 |
| `nativeCompile` 빌드 | ✅ 성공 (25.2s) |
| **네이티브 실행** | ❌ `Fatal error reported via JNI: Could not allocate library name` |

### Codex가 놓친, 더 결정적인 근거

Codex는 런타임 JNI 오류를 실패 근거로 들었다. 그런데 산출물 목록을 보니
실행 파일 옆에 **AWT 사이드카 `.so` 8개**가 생성돼 있었다.
직접 격리 테스트를 해봤다:

```
$ cp ats-check /tmp/ && /tmp/ats-check --resume resume.pdf
UnsatisfiedLinkError: No awt in java.library.path
```

**JNI 오류를 고쳐도 소용없다.** 배포 산출물이 `17MB 파일 1개` → `43MB 파일 9개`가 되고,
"바이너리 하나 받아서 실행"이라는 제품 전제 자체가 무너진다.
이건 튜닝으로 풀 문제가 아니라 스코프 결정이 필요한 문제다.

### 기각한 우회책

1. PDFBox JAR의 GraalVM 메타데이터 → **없음**
2. Reachability Metadata Repository 활성화 → 빌드 통과, **런타임 실패 동일**
3. 수동 `reflect-config` → **불가.** `MissingReflectionRegistrationError`가 안 떠서
   등록할 클래스를 특정할 수 없었다
4. `-H:+AddAllCharsets` → charset 경고만 해소
5. `--initialize-at-build-time` → **빌드 실패.** 22개 이상 연쇄 초기화
   (`java.awt.Toolkit`, `BufferedImage`, `ICC_Profile` …)

### 결정

**이력서 파싱(PDF/DOCX)을 v0.2로 연기.** 헌장 §11이 미리 정해둔 분기를 그대로 실행했다.

제품은 성립한다 — §7이 `profile.yml`만으로 전 단계가 동작하도록 설계해뒀기 때문이다.
이력서 파싱은 편의 기능이지 전제가 아니다.

DOCX(POI)는 실측하지 않았다. AWT 결합이 더 심해 같은 실패가 예상되므로,
두 번째 스파이크에 시간 쓰는 대신 이력서 경로 전체를 일관되게 미뤘다.
**추정이라는 점을 ADR-005에 명시했다.**

실험 코드는 `spike/pdfbox` 브랜치에 보존하고 병합하지 않았다.

커밋: `98fdfa6` / 문서: `docs/adr/ADR-005-no-pdf-parsing-in-v0.1.md`

## 3. 헌장 개정 반영

사용자가 `save`/`open`/프론트매터/상태추적을 추가했다. 반영하면서
**네이티브 빌드를 깨뜨릴 수 있는 신규 리스크 2건과 규격 충돌 1건**을 함께 확정했다.

| # | 문제 | 조치 |
|---|---|---|
| 1 | `save`가 클립보드를 AWT로 읽으면 **PDFBox와 똑같이** `java.desktop`을 끌어온다 | 외부 명령 위임 (`wl-paste`/`pbpaste`/`Get-Clipboard`), `open`도 `xdg-open`/`open`/`start` |
| 2 | `save` 성공(exit 0)이 **"APPLY"와 구분되지 않는다** | `check`만 판정 코드(0/1/2), 나머지 서브커맨드는 `0=성공` |
| 3 | 저장된 공고 원문이 **공개 레포에 커밋될 수 있다** | `jobs/`를 `.gitignore`에 (§9 익명화 정책과 충돌) |
| 4 | SnakeYAML 클래스 바인딩은 리플렉션 메타데이터를 요구 | `Map` 파싱 후 수동 매핑 |
| 5 | OSC 8 하이퍼링크가 파이프에 섞이면 스크립트 연동이 깨진다 | 비-TTY에서 자동 비활성화 |

DoD에 **"각 바이너리가 단일 파일이다"**를 추가하고, CI 스모크 테스트는
바이너리를 다른 디렉토리로 복사해서 실행하도록 명시했다. 같은 함정을 CI가 잡는다.

§2 판단 기준에도 4번을 추가했다: **"단일 바이너리 배포를 깨뜨리는가"**

## 5. Task 1 — 섹션 분류기

### 설계에서 보완한 것

헌장 §6은 2층 신호(섹션 헤더 + 문장 어조)를 제시한다. 그런데 **그것만으로는
§6 자신의 예시를 처리할 수 없다:**

```
"Working knowledge of Finnish"   → §6은 REVIEW를 원한다
```

이 문장이 `Requirements:` 섹션 안에 있으면 2층 신호로는 REQUIRED가 되어버린다.
그래서 **완화 표현(hedge)을 3층 신호로 추가**했다 —
`working knowledge`, `basic`, `conversational` 등이 확신을 깎는다.

결합 규칙을 10행 표로 확정하고 전부 테스트로 덮게 지시했다.

### Codex 산출물

- 모델 4개(`RequirementLevel`, `SectionKind`, `Signal`, `Clause`) + 분류기 4개
- 테스트 18개 통과, `core` 런타임 의존성 여전히 0개
- §6의 세 예시 정확히 동작 ✅

보고서 §6("스스로 결정한 것")을 성실히 채웠고, §8에서 **자기 산출물의 리스크를
정확히 지적**했다. 그 지적이 맞는지 직접 확인했다.

### 2차 검증에서 잡은 결함 3건

컴파일된 클래스를 직접 호출해 실제 공고 패턴을 넣어봤다:

| 입력 | 결과 | 문제 |
|---|---|---|
| `Finnish is not required.` | **REQUIRED** ❌ | **치명적.** 핀란드어가 *불필요*한 좋은 공고를 SKIP시킨다. 도구 목적과 정반대 |
| `Benefits:` → `Free Finnish lessons.` | **REQUIRED** ❌ | 복지를 필수 요건으로 오독. 핀란드 회사가 "Finnish lessons provided"를 복지로 적는 건 흔하다 |
| `Requirements include Java and Kotlin.` | **절이 0개** ❌ | 헤더로 오탐되어 요건이 통째로 소실 |

**왜 이게 지금 중요한가:** 판정 규칙(Task 2)이 이 분류기 위에 얹힌다.
분류가 틀리면 언어·연차·학위·스킬 규칙이 전부 틀린다. 다음 단계로 넘어가기 전에 고쳐야 한다.

### Task 1.5 — 수정 완료 ✅ (커밋 `5330f59`)

1. **부정 신호를 4번째 축으로 추가** — `RequirementLevel.NEGATED` 신설.
   `NICE`로 뭉뚱그리지 않는다. "있으면 좋다"와 "필요 없다"는 의미도 출력 문구도 다르다.
   대조 접속사(`but`, `however`)가 있으면 부정 범위가 불확실하므로 `AMBIGUOUS`
2. **헤더 판정을 형태 기반으로** — 문장 종결 부호로 끝나는 줄은 헤더가 아니다
3. **미지 헤더에서 섹션 상태 리셋** — 모르면 중립으로 두는 것이 §6의 "단정하지 않는다" 원칙에 맞다.
   중립 헤더 사전(`benefits`, `perks`, `about us`, `tech stack` …)도 명시

재현 케이스 3건을 그대로 테스트로 넣게 했고, **기존 18개 테스트 회귀 금지**를 조건에 걸었다.

### 수정 결과 (재검증 실측)

| 케이스 | 수정 전 | 수정 후 |
|---|---|---|
| `Finnish is not required.` | REQUIRED ❌ | **NEGATED** ✅ |
| `Finnish is not mandatory.` | REQUIRED ❌ | **NEGATED** ✅ |
| `Benefits:` → `Free Finnish lessons.` | REQUIRED ❌ | **UNKNOWN** ✅ |
| `Benefits:` 줄 자체 | 절로 포함됨 ❌ | **제거됨** ✅ |
| `Requirements include Java and Kotlin.` | 절 0개 ❌ | **절로 잡힘** ✅ |
| `We expect you to ship code.` | 절 0개 ❌ | **REQUIRED** ✅ |
| §6 세 예시 | ✅ | ✅ **회귀 없음** |

테스트 18 → **32개**, `core` 런타임 의존성 여전히 **0개**.

남은 리스크는 전부 **안전한 방향**이라 v0.1에서 수용한다:
`not strictly required` 같은 변형은 미탐될 수 있고, `while`을 대조 접속사로 오인하면
`AMBIGUOUS`(→ REVIEW)가 된다. **틀린 SKIP보다 정직한 REVIEW가 낫다**는 ADR-002의 원칙과 같다.

## 6. Task 2 — Stage 1 하드 필터 ✅ (커밋 `c25e097`)

언어·연차·학위 3개 규칙. **이 도구 가치의 대부분이 여기 있다.**

### 설계에서 확정한 것

**`core` 의존성을 계속 0개로 유지한다.** 헌장 §3은 "core는 이상적으로 SnakeYAML만"이라 하지만,
`profile.yml`을 읽는 것은 파일 I/O이므로 `cli`의 책임이다. `core`는 완성된 `Profile` 객체를
받기만 한다. ADR-004의 경계 원칙과도 맞고, ADR-005에서 배운
"의존성 하나가 단일 바이너리를 깨뜨린다"는 교훈에도 맞다.

**기본 프로필은 아무것도 걸러내지 않는 쪽으로 잡았다** (`maxSeniority=LEAD`, `degree=NONE`).
설정 없이 쓰는 사용자에게 근거 없는 SKIP을 주면 도구 신뢰가 무너진다.

**`NEGATED`를 PASS로 처리하는 것이 언어 규칙의 핵심**이고, 이는 Task 1.5에서 고친
결함의 회귀 방지 테스트로 명시했다.

**학위 규칙의 `master` 오탐 방지** — `"master of your craft"`, `"mastery"`는 학위가 아니다.
학위 문맥 단어(`degree`, `education`, `university`)가 같은 절에 있을 때만 인정하도록 지시했다.
`"or equivalent experience"`가 있으면 `FAIL` → `WARN`으로 낮춘다.

### 2차 검증 — 실제 공고 형태로 직접 실행

테스트 68개가 통과했지만, 테스트는 Codex가 스스로 짠 것이므로 **별도로 실제 공고를 넣어봤다.**

| 시나리오 | LANGUAGE | EXPERIENCE | DEGREE |
|---|---|---|---|
| 핀란드어 필수 + 7년 + MSc | **FAIL** | **FAIL** | **FAIL** |
| `Finnish is not required` + 2년 + 학사 | PASS<br>*"explicitly not required"* | PASS | PASS |
| 복지의 `Free Finnish lessons` | **PASS** | PASS | PASS |
| `3+ years` + `MSc or equivalent` | PASS | **WARN**<br>*borderline* | **WARN**<br>*완화 적용* |
| `Working knowledge of Finnish` | **REVIEW** | PASS | PASS |
| `master of your craft` + `PhD is a plus` | PASS | PASS | **PASS**<br>*오탐 없음* |

전부 기대대로다. 근거 원문도 정확히 담겼다 (§6 요구사항).

**세 번째 행이 이 프로젝트에서 가장 중요한 검증이다.** Task 1.5에서 고친 분류기 수정이

## 7. Task 3 + 3.5 — `core` 완성 ✅ (커밋 `a0a963a`)

### 설계에서 확정한 것

**시니어리티는 직무명에서만 찾는다.** 본문을 스캔하면
`"you will work with senior engineers"` 같은 문장이 오탐을 만든다.

**Stage 1은 FAIL이 나와도 세 규칙을 전부 실행한다.** §8의 SKIP 출력 예시가
탈락 사유 외의 검사 결과도 함께 보여주기 때문이다. "stopped at hard filter"가 뜻하는 것은
Stage 2·3을 건너뛴다는 것이지 Stage 1을 중간에 멈춘다는 뜻이 아니다.

**`WARN`은 verdict를 바꾸지 않는다.** §5가 "`max_seniority` 초과는 WARN (SKIP 아님)"이라고
명시했고, 스킬 부족도 SKIP 사유가 아니다 (§8 예시에서 `MISSING (required)`가 있는데도 APPLY).

**스킬 매칭의 함정을 미리 지시했다** — `c`가 `"can"`에, `go`가 `"going"`에 걸리면 안 되고,
`c++`/`c#`/`.net`은 정규식 이스케이프가 필요하며, `"spring boot"`가 `"spring"`으로
잘리지 않도록 긴 항목을 먼저 매칭해야 한다.

### 2차 검증 — 판정 조립은 사양대로

| 검증 | 결과 |
|---|---|
| 핀란드어 필수 → `SKIP`, `stoppedAtHardFilter`, skillGap=null | ✅ |
| SKIP인데도 Stage 1 검사 3개 모두 표시 | ✅ (§8 출력 예시 요구) |
| §8 APPLY 예시 → `MISSING(required) [kotlin, kubernetes]` / `MISSING(nice) [terraform]` | ✅ |
| 애매한 핀란드어 → `REVIEW` | ✅ |
| `Senior Backend Engineer` → WARN이지만 **APPLY 유지** | ✅ (§5 요구) |
| 본문의 `work with senior engineers` 무시 | ✅ |

### 그러나 스킬 매칭에서 결함을 또 잡았다 → Task 3.5

지시서에 함정을 미리 적어뒀는데도 **일상 영단어가 기술명으로 잡혔다.**
단어 경계(`\b`)만으로는 부족했던 것이다.

| 입력 | 수정 전 | 수정 후 |
|---|---|---|
| `We can go fast and ship often.` | `[go]` ❌ | `[]` ✅ |
| `A swift and clear communication style.` | `[swift]` ❌ | `[]` ✅ |
| `You are a rust-free engineer.` | `[rust]` ❌ | `[]` ✅ |
| `We work in a scala-ble architecture.` | `[scala]` ❌ | `[]` ✅ |
| `Golang microservices experience.` | `[microservices]` ❌ | `[go, microservices]` ✅ |
| `Experience with Go and Rust.` | `[go, rust]` | `[go, rust]` ✅ 회귀 없음 |
| `k8s and postgres` | — | `[kubernetes, postgresql]` ✅ 정규화 |

**세 가지로 고쳤다:**
1. **하이픈 경계 강화** — 매칭 앞뒤가 단어 문자면 거부 (`rust-free`, `scala-ble`)
2. **모호한 기술명은 문맥을 요구** — `go`/`swift`/`rust`/`scala`/`c`는 같은 절에
   기술 문맥 단어가 있거나, `experience with` 패턴이거나, 명확한 다른 기술과 나열될 때만 인정.
   `engineer`/`developer`는 문맥 단어에서 **제외**했다 — 너무 흔해서

3. **별칭 정규화** — `golang`→`go`, `k8s`→`kubernetes`, `postgres`→`postgresql`,

**왜 골든 파일 전에 고쳤나:** 스킬 갭은 verdict를 바꾸지 않으므로 치명적이지 않다.
그러나 골든 파일은 회귀 방지의 **기준선**이다. 잘못된 동작을 기준선으로 굳히면
나중에 되돌리기 어렵다.

## 9. Task 5 + 5.5 — CLI 실전화 ✅ (커밋 `ba0396d`, `11cde0e`)

Day 10-13 시작. Spike A의 "파일을 읽어 그대로 출력하는" 스텁을 실제 도구로 바꾼다.

### 설계에서 확정한 것

**`--json`일 때 stdout에는 JSON만 내보낸다.** 안내 메시지는 전부 stderr로 보낸다.
스크립트 연동이 목적인 플래그이므로 한 줄이라도 섞이면 쓸모가 없다.

**JSON writer를 직접 구현한다.** SnakeYAML의 dump는 YAML을 뱉는다.
스키마가 작으므로 손으로 쓰되 문자열 이스케이프를 정확히 처리하게 했다.

**`profile.yml`은 `Map`으로만 읽는다** (§7 규칙). 클래스 바인딩은 네이티브에서
리플렉션 메타데이터를 요구한다. 잘못된 값(`max_seniority: wizard`)은 조용히 무시하지 않고
경고 후 기본값을 쓴다.

**`--profile`로 지정한 경로가 없으면 exit 64.** 탐색 경로에 파일이 없는 것(기본값 사용)과
사용자가 명시한 파일이 없는 것(사용법 오류)은 다르다.

**종료 코드 테스트 14개를 요구했다.** §9가 "종료 코드는 제품 계약"이라고 명시했고,
현재 `cli`에는 테스트가 하나도 없다.

### 가장 중요한 완료 조건

**SnakeYAML을 추가한 뒤에도 네이티브 빌드가 단일 파일로 유지되는지 확인.**
바이너리를 다른 디렉토리로 복사해 실행하고, 사이드카 `.so`가 하나라도 생기면
즉시 멈추고 보고하도록 지시했다. ADR-005에서 PDFBox로 겪은 일이다.

### 결과 — 가장 중요한 확인부터

**네이티브 빌드가 단일 파일 19MB로 유지된다.** 사이드카 `.so` 없음.
다른 디렉토리로 복사해 실행해도 정상 동작한다. SnakeYAML은 안전한 의존성이었다.

| 검증 (네이티브 바이너리 실측) | 결과 |
|---|---|
| APPLY / REVIEW / SKIP | exit **0 / 1 / 2** ✅ |
| 파일 없음 / `--profile` 경로 없음 / 빈 입력 | exit **64** ✅ |

| 안내 메시지 | stderr로 분리 (70B) ✅ |
| 격리 실행 (사이드카 없이) | 정상 ✅ |

### 그러나 출력 형식이 §8과 어긋났다 → Task 5.5

동작·판정·종료 코드는 전부 정확했지만 **표시가 사양과 달랐다.**

| 항목 | 수정 전 | §8 사양 / 수정 후 |
|---|---|---|
| 라벨 폭 | 10칸 | **12칸** |
| 표시 순서 | Language→Seniority→Degree→Level | **Language→Level→Seniority→Degree** |
| Level | `no seniority marker` | **`Backend Engineer (no seniority marker)`** |
| 스킬 표시 | `kotlin, kubernetes` | **`Kotlin, Kubernetes`** |
| WARN | (없음) | **`— borderline`** |

**핵심 지시:** 표시 순서와 실행 순서는 별개다. `--json`과 골든 테스트가 실행 순서에
의존하므로 **렌더러만 정렬**하게 했다. 스킬 이름도 JSON에는 정규화된 소문자를 유지시켰다
— 스키마 안정성(§8)이 표시 예쁨보다 우선한다.

스킬 표시는 단순 capitalize 대신 **표시 이름 맵**을 만들게 했다.
`postgresql`→`PostgreSQL`, `c++`→`C++`, `node.js`→`Node.js`처럼 naive하게 대문자화하면
어색해지는 값이 많다. 맵에 없으면 원본 그대로 둔다.

```
  ✓ Degree      not required

  MISSING (required)   Kotlin, Kubernetes
  MISSING (nice)       Terraform
  MATCHED              Java, Spring Boot, PostgreSQL, REST
```

## 10. Task 6 — save / open / init (진행 중)

`save`가 배치 모드의 전제다. 본문만 저장하면 판정 결과에서 원래 공고로 돌아갈 수 없다.

### 설계에서 확정한 것

**AWT 금지를 지시서 최상단에 못박았다.** `Toolkit.getSystemClipboard()`와
`Desktop.browse()`는 `java.desktop`을 끌어와 **PDFBox와 똑같이** 단일 바이너리를 깨뜨린다.
외부 명령(`wl-paste`/`xclip`/`pbpaste`/`Get-Clipboard`, `wslview`/`xdg-open`/`open`/`start`)에
위임하고, 전부 실패하면 stdin으로 폴백한다. **5초 타임아웃**도 걸게 했다 — 명령이 멈추면
CLI가 같이 멈춘다.

**클립보드·브라우저는 인터페이스로 추상화**해서 테스트에서 가짜를 주입하게 했다.
실제 명령을 실행하는 테스트는 CI에서 환경에 따라 깨진다.

**stdin이 파이프면 클립보드보다 우선한다.** 파이프 입력이 있다는 건 명시적 의도다.

**`--all-apply`가 10개를 넘으면 열지 않고 목록만 출력**하도록 했다. 브라우저 탭 폭탄 방지.
`--force`로 우회할 수 있다.

**`init`은 대화형 질문을 하지 않는다.** 파이프나 CI에서 멈춘다. 주석 달린 템플릿을 쓰고
편집을 안내한다. 생성한 파일을 `ProfileLoader`가 읽을 수 있는지 왕복 테스트도 요구했다.
