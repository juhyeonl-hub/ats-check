# ADR-003: Linux 네이티브 바이너리는 구버전 컨테이너 안에서 빌드한다

- 상태: **채택됨**
- 날짜: 2026-08-15

## 맥락

`ats-check`는 GitHub Releases에 3개 OS의 네이티브 바이너리를 올린다.
사용자는 바이너리를 내려받아 바로 실행한다.

GitHub Actions의 `ubuntu-latest` 러너에서 `native-image`를 그냥 돌리는 것이 가장 간단하다.
그런데 GraalVM native-image로 만든 Linux 바이너리는 **glibc에 동적으로 링크**되고,
**빌드 머신의 glibc 버전보다 낮은 시스템에서는 실행되지 않는다.**

## 측정

로컬(Ubuntu 22.04, glibc 2.35)에서 빌드한 바이너리를 조사했다:

```
$ objdump -T ats-check | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -3
GLIBC_2.17
GLIBC_2.32
GLIBC_2.34

$ ldd ats-check
  linux-vdso.so.1
  libz.so.1 => /lib/x86_64-linux-gnu/libz.so.1
  libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
  /lib64/ld-linux-x86-64.so.2
```

**이 바이너리는 `GLIBC_2.34` 이상을 요구한다.**

| 배포판 | glibc | 실행 가능 |
|---|---:|---|
| Ubuntu 24.04 | 2.39 | ✅ |
| Ubuntu 22.04 | 2.35 | ✅ |
| **Ubuntu 20.04** | 2.31 | **❌** |
| Debian 12 | 2.36 | ✅ |
| **Debian 11** | 2.31 | **❌** |
| RHEL 9 | 2.34 | ✅ (경계) |
| **RHEL 8** | 2.28 | **❌** |

`ubuntu-latest` 러너는 이보다 더 새로운 glibc를 쓰므로 상황이 나빠지기만 한다.
**러너에서 그냥 빌드하면 아직 널리 쓰이는 LTS 배포판 사용자가 바이너리를 실행할 수 없다.**

## 결정

**Linux 네이티브 빌드는 구버전 베이스 이미지 컨테이너 안에서 수행한다.**

`ubuntu:20.04`(glibc 2.31)를 기준으로 삼는다. macOS와 Windows는 이 문제가 없으므로
러너에서 직접 빌드한다.

## 근거

### 1. 하위 호환은 빌드 시점에만 만들 수 있다

바이너리가 요구하는 glibc 심볼 버전은 **링크 시점에 결정된다.**
배포 후에는 되돌릴 방법이 없다. "낮은 쪽에서 빌드해 높은 쪽에서 실행"은 되지만
그 반대는 안 된다.

### 2. 이것이 이 프로젝트에서 Docker를 쓰는 유일한 이유다

`CLAUDE.md` §2는 **Docker 배포를 금지**한다.
네이티브 바이너리를 만드는 이유가 컨테이너를 안 쓰기 위해서이기 때문이다.

여기서 Docker는 **배포 수단이 아니라 빌드 도구**다.
사용자는 Docker를 설치하지 않고, 컨테이너를 실행하지도 않는다.
CI가 빌드할 때만 쓰고 산출물은 여전히 단일 바이너리다. 금지 조항과 충돌하지 않는다.

### 3. 기각한 대안

**(a) `ubuntu-latest`에서 그냥 빌드**
가장 간단하지만 위 표대로 LTS 사용자를 배제한다. 기각.

**(b) 정적 링크 (`--static` + musl)**
glibc 의존을 완전히 없앤다. 그러나:
- musl 툴체인을 별도로 준비해야 하고 CI가 복잡해진다
- musl과 glibc는 DNS 해석·로케일 처리가 다르다. 지금은 네트워크를 안 쓰지만
  향후 v0.2의 `fetch`에서 문제가 될 수 있다
- 이 프로젝트의 목적(구직 도구)에 비해 과한 복잡도다

컨테이너 빌드로 충분한 호환성을 얻으므로 채택하지 않는다. **v0.2에서 재검토할 수 있다.**

**(c) 여러 glibc 버전으로 여러 바이너리 배포**
릴리스 자산이 늘고 사용자가 고민해야 한다. 단일 바이너리 원칙에 어긋난다. 기각.

## 결과

- 릴리스 워크플로의 Linux job은 `ubuntu:20.04` 컨테이너에서 `native-image`를 실행한다
- 컨테이너 안에 GraalVM CE 21과 빌드 도구(`gcc`, `zlib1g-dev`)를 설치한다
- **릴리스 스모크 테스트는 반드시 바이너리를 다른 디렉토리로 복사해서 실행한다.**
  ADR-005에서 PDFBox가 사이드카 `.so`를 만들었을 때, 원래 위치에서만 동작하고
  복사하면 죽는 상태였다. 이 검사가 그것을 잡는다
- macOS/Windows는 러너에서 직접 빌드한다

## 검증 방법

CI에서 Linux 바이너리를 빌드한 뒤 확인한다:

```bash
objdump -T ats-check | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -1
```

`GLIBC_2.31` 이하가 나와야 한다. 그보다 높으면 컨테이너 설정이 잘못된 것이다.

## 미확인 사항

이 결정은 **로컬 빌드 실측**에 근거한다.
컨테이너 빌드가 실제로 `GLIBC_2.31` 이하를 만들어내는지는 **CI에서 확인해야 한다.**
확인 후 이 문서를 갱신한다.
