# ADR-002: 판정에 LLM을 쓰지 않는다

- 상태: **채택됨**
- 날짜: 2026-08-15

## 맥락

"이 공고가 필수로 요구하는 것이 무엇인가"를 판단하는 일은 자연어 이해 문제다.
LLM에게 공고를 통째로 넘기고 JSON으로 판정을 받아오면 규칙을 한 줄도 안 짜도 된다.

## 결정

**LLM/AI API를 호출하지 않는다.** 규칙 기반으로 구현한다.

## 근거

### 1. 정확도가 더 높다 — 이 문제에 한해서

이 도구가 푸는 문제는 열린 자연어 이해가 아니라 **좁고 반복적인 패턴 매칭**이다.

```
"Fluent Finnish required"        → 필수
"Finnish is a plus"              → 우대
"Working knowledge of Finnish"   → 애매
```

채용 공고는 놀랄 만큼 정형화된 문서다. 섹션 헤더(`Requirements:`, `Nice to have:`)와
어조 마커(`must`, `is a plus`)가 반복된다. 이 구조에는 규칙이 잘 맞는다.

반대로 LLM은 **같은 입력에 다른 답을 줄 수 있다.** 지원 여부를 거르는 도구에서
비결정성은 치명적이다. 사용자가 "왜 이게 SKIP이지?"라고 물었을 때 답할 수 없다.

### 2. 설명 가능해야 한다

§6은 **"원문 문장을 반드시 함께 출력한다"**고 요구한다.

```
✗ Language    Finnish required
              "Fluent Finnish and English are required"
```

규칙 기반이면 어떤 사전 항목이 어느 줄에 걸렸는지 정확히 추적된다.
LLM은 근거 문장을 지어낼 수 있고(환각), 그 순간 도구의 신뢰가 무너진다.
**모호한 것을 억지로 판정하지 않고 REVIEW로 내보내는 것**이 이 도구의 신뢰 전략인데,
LLM은 모호함을 자신 있게 단정하는 쪽으로 기운다.

### 3. 빠르고 무료다

| | 규칙 기반 | LLM |
|---|---|---|
| 단건 판정 | 밀리초 | 수 초 |
| 100건 배치 | 즉시 | 수 분 + 비용 |
| 비용 | 0 | 토큰 과금 |
| 오프라인 | 동작 | 불가 |

배치 모드(`--job-dir`)에서 차이가 결정적이다.

### 4. 제품 정체성과 충돌한다

§1의 차별점은 **"로컬에서만 처리, 네트워크 호출 0"**이다.
LLM API를 부르는 순간 사용자의 공고 데이터(그리고 이력서 정보)가 외부로 나간다.
경쟁 도구와 구분되는 유일한 지점을 스스로 버리는 셈이다.

### 5. 네이티브 바이너리와 맞지 않는다

HTTP 클라이언트와 JSON 파서가 들어오면 의존성이 늘고, GraalVM native-image에서
리플렉션 메타데이터 문제가 생긴다. ADR-005에서 확인했듯 **의존성 하나가
단일 바이너리 배포를 깨뜨릴 수 있다.**

## 결과

- 판정은 `core` 모듈의 순수 함수로 구현한다
- 사전(섹션 헤더·어조 마커·완화 표현)은 상수로 두고 확장 가능하게 한다
- 오탐/미탐은 **골든 파일 테스트 30개**로 잡는다. 규칙을 고칠 때마다 CI가 회귀를 막는다

## 인정하는 한계

규칙 기반은 사전에 없는 표현을 놓친다. 특히 비영어권 회사의 독특한 영어 표현이나
새로운 완곡 표현이 그렇다.

이를 **설계로 흡수한다**: 신호가 없으면 `REQUIRED`로 단정하지 않고 `UNKNOWN`으로 두고,
충돌하면 `AMBIGUOUS`로 내보낸다. 결과적으로 `REVIEW` 판정이 나오고,
사용자는 원문을 직접 읽는다. **틀린 SKIP보다 정직한 REVIEW가 낫다.**
