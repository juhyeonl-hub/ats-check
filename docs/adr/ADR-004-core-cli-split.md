# ADR-004: `core`와 `cli`를 별도 모듈로 분리한다

- 상태: **채택됨**
- 날짜: 2026-08-15

## 맥락

`ats-check`는 단일 실행 파일 하나를 만든다. 모듈이 하나여도 빌드된다.
멀티모듈은 빌드 스크립트를 늘리고 Gradle 설정을 복잡하게 만든다.

## 결정

**두 모듈로 나눈다.**

| 모듈 | 책임 | 의존성 |
|---|---|---|
| `core` | 판정 로직. 문자열 in → 판정 out | **0개** (이상적으로 SnakeYAML만) |
| `cli` | Picocli, 파일 I/O, 출력 포매팅, 외부 명령 호출 | Picocli 외 |

`core`는 **파일도 네트워크도 stdout도 모른다.**

## 근거

### 1. 의존성 오염을 구조로 막는다 — 실제로 작동했다

이것이 가장 큰 이득이며, **이미 값을 했다.**

ADR-005에서 PDFBox가 `java.desktop`/AWT를 끌어와 단일 바이너리 배포를 깨뜨렸다.
PDFBox를 `cli`에만 넣었기 때문에 **`core`는 오염되지 않았고, PDF 지원을 들어내는 데
`cli` 쪽 코드만 지우면 됐다.** `core`의 판정 로직은 손댈 필요가 없었다.

모듈이 하나였다면 AWT 의존이 판정 로직과 뒤엉켜, 되돌리는 비용이 훨씬 컸을 것이다.

이 경험을 규칙으로 승격했다: **`core`에 의존성을 추가할 때는 네이티브 빌드부터 확인한다.**

### 2. 테스트가 빨라지고 단순해진다

`core`는 순수 함수라 파일 시스템도 임시 디렉토리도 필요 없다.

```java
assertThat(classifier.classify("Finnish is a plus"))
    .extracting(Clause::level).containsExactly(NICE);
```

골든 파일 테스트 30개가 목표인데(§9), I/O가 섞이면 테스트가 느려지고 플레이키해진다.
커버리지 목표를 `core` 80% / `cli` 무목표로 나눈 것도 이 분리 덕분에 가능하다.

### 3. 재사용 경로를 열어둔다

v0.3 백로그에 "Maven Central에 `core` 모듈 배포"가 있다.
브라우저 확장이나 웹 API를 얹는 선택지도 열려 있다.
`core`가 I/O를 모르기 때문에 **어떤 실행 환경에도 얹을 수 있다.**

로직이 CLI 파싱과 뒤엉켜 있으면 이 경로는 전부 막힌다.

### 4. 경계가 설계를 강제한다

"`core`는 `System.out`을 쓸 수 없다"는 제약은 불편이 아니라 **설계 압력**이다.
판정 결과를 출력하려면 `Clause`가 근거 신호와 원문을 데이터로 들고 있어야 한다.
그 결과 §6이 요구하는 "원문 문장을 함께 출력한다"가 자연스럽게 충족된다.

출력을 아무 데서나 할 수 있었다면 로직 중간에 `println`이 흩어졌을 것이다.

## 검증

이 경계는 문서가 아니라 **테스트로 강제한다.**

```bash
grep -rniE "java\.net|HttpClient|Socket|System\.out|System\.err|java\.io\.File|Files\." core/src/main/
```

Spike A 검증에서 이 grep이 통과했다 (결과: 없음). CI에 추가한다.

## 비용

- Gradle 설정 파일이 3개가 된다 (`settings`, `core`, `cli`)
- 모듈 간 이동이 필요해 IDE 탐색이 약간 번거롭다

**빌드 시간에는 영향이 없다.** Spike A 실측에서 clean 빌드가 1초, native-image가 17초였고
병목은 전적으로 native-image 단계다.
